## Issues

### Issue 1 (MUST-FIX): Task 2 leaves the unit suite red until Task 3 completes — violates "keep the tree green at each step"

**What's wrong:** Task 2 renames the export `CHORD_SYMBOL_SIZE → NOTE_SIZE` in `constants.js`, but `layout.js` (`import { … CHORD_SYMBOL_SIZE … }` at `layout.js:33`) and `svg.js` (`constants.js` import at `svg.js:32`) still import `CHORD_SYMBOL_SIZE`, and those importers are not fixed until Task 3. Under `@wordpress/scripts` (Babel + CJS interop) a missing named import resolves to `undefined` rather than throwing at load, so `topMarginLayout` computes `topExtent = d + undefined = NaN` and `renderHandText` emits `font-size: undefined` — the layout and svg unit suites go red. Task 2's own Acceptance concedes this ("layout.js/svg.js … will not build/test until Tasks 3/6/7 … the code-writer should … not expect the full suite green until Task 3"). The plan's own Overview (line 7: "each layer lands with its tests before the next depends on it") and the orchestrator's hard review criterion — "the sequence keeps the tree green at each step (code-writers run sequentially in one tree, TDD)" — are both violated for the Task 2 → Task 3 window. A code-writer dispatched for Task 2 doing TDD cannot reach green, and the next code-writer inherits a red tree.

**Where in plan:** Task 2 (Changes: "Rename the export `CHORD_SYMBOL_SIZE` … to `NOTE_SIZE`"; Acceptance: "`CHORD_SYMBOL_SIZE` is no longer exported" and the parenthetical "will not build/test until Tasks 3/6/7").

**Suggestion:** Make the rename green at every step. Two clean options:
- (a) In Task 2, **add** `NOTE_SIZE` as the new export and keep `CHORD_SYMBOL_SIZE` as a temporary re-export/alias (`export const CHORD_SYMBOL_SIZE = NOTE_SIZE;` or `export { NOTE_SIZE as CHORD_SYMBOL_SIZE }`). Then in Task 3, after the `layout.js`/`svg.js` importers are switched to `NOTE_SIZE`, delete the alias — the existing token-removal grep in Task 3 already enforces that the alias is gone. This keeps Task 2 self-contained and green.
- (b) Fold the `CHORD_SYMBOL_SIZE → NOTE_SIZE` rename (and the importer updates) entirely into Task 3, leaving Task 2 to only **add** the four new constants (which have no existing importers, so Task 2 stays trivially green).
Either way, update Task 2's Acceptance to require the full unit suite green (drop the "not expect the full suite green until Task 3" carve-out).

**Why it matters:** "Build-safe ordering / green at each step" is a named hard requirement for this review. A red intermediate step removes the TDD safety net for the most error-prone task in the plan (the cross-file rename) and can mask an unrelated regression introduced in Task 2 or Task 3 because there is no clean checkpoint between them. The fix is a one-line alias and costs nothing.

### Issue 2 (SHOULD-FIX): Task 5 X-clamp formula mixes a measure-relative term with an absolute (system-coordinate) term

**What's wrong:** Task 5 specifies the standalone X resolution as `x = min( beatToX(min(beat, measureEnd)), measureRightX − NOTE_CLAMP_INSET )`, where `beatToX` interpolates over the `columnX` grid. In the actual code, `columnX` is **measure-relative** (`layout.js:1404` JSDoc: "Onset → relative X within the measure"; `cx` starts at `leadInset`, `layout.js:1773`), but `measureRightX` is **absolute / system-coordinate** (`measureRightX = x + scaledContent`, `layout.js:1804`, where `x` is the measure's absolute X). Mixing the two inside one `min(...)` is a frame error: for any measure after the first (`x > 0`), `measureRightX − NOTE_CLAMP_INSET` is far larger than the relative `beatToX(...)`, so the clamp silently never fires, and if a writer instead stored the *absolute* clamp result on the primitive it would be double-translated by the `<g data-measure transform="translate(measure.x 0)">` at emit (`svg.js:471`) and land a full `measure.x` too far right. The plan flags the frame requirement in prose ("ensure the value stored … is in the same coordinate frame the per-event/measure-relative X values use"), and Task 5 even calls `measureRightX` "measure-local" — but it is **not** measure-local in the code, so the prose contradicts the cited variable. Note the barline path sidesteps this by storing absolute X and subtracting `measureX` back at emit (`svg.js:735`), which is the opposite convention from the per-event `texts` path (relative X, no subtraction) that standalone notes must match.

**Where in plan:** Task 5, Changes → "Over-content clamp" bullet ("`measureRightX` here is measure-local — the same value the barline uses, expressed relative to the measure group").

**Suggestion:** State the clamp in the measure-relative frame explicitly so both terms agree and the emit (Task 8) can drop the primitive under `<g data-measure>` with no subtraction. Concretely: use the measure-relative right edge `scaledContent` (which equals `measureRightX − x`) rather than `measureRightX`, i.e. `x = min( beatToX(min(beat, measureEnd)), scaledContent − NOTE_CLAMP_INSET )`, with `beatToX` resolving over the relative `columnX` grid (last column extending to `scaledContent`/content right edge). Correct the prose: `measureRightX` as defined at `layout.js:1804` is **absolute**, not measure-local; either compute the relative edge as shown, or, if the absolute `measureRightX` is genuinely wanted, store absolute X and have Task 8 subtract `measure.x` back the way `renderBarline` does — but then say so, because that diverges from the per-event `texts` convention.

**Why it matters:** Two code-writers reading "measure-local `measureRightX`" against a variable that is actually absolute will produce different X frames, so the plan fails the "two independent code-writers produce the same change" bar, and the most likely outcome (clamp never fires, or node translated `measure.x` too far) directly breaks the spec ACs Task 5/8 trace to: over-content `beat: 99` "within the system's horizontal bounds" and the `beat: 0` vs `beat: 2` ordering for non-first measures. This is a self-contained-task hazard since each task is dispatched verbatim.
