## Issues

### Issue 1 (MUST-FIX): Task 5's standalone record shape omits the raw `beat` that Task 8 needs to group/stack same-anchor standalone notes — and the two tasks contradict each other

**What's wrong:** Task 8 stacks standalone notes by group: "Stack k by the note's index within its `(staff, placement, raw beat ?? "noBeat")` group from Task 5" (plan line 257), and its acceptance asserts "N standalone notes of the same `(staff, placement, beat)` emit N nodes at N distinct Ys" (line 272). To compute that group key, Task 8 must read the **raw** `beat` off each `measureModel.standaloneNotes` record. But Task 5 specifies the record as carrying "`x`, `text`, `placement`, `staff` **only**" (line 156) and its acceptance lists exactly "`kind: "note"`, `text`, `placement`, and `staff`" (line 165) — raw `beat` is not stored. Task 5 line 157 hedges ("record enough on the primitive (or keep array order within a group) that Task 6/7 can stack same-anchor notes"), which both (a) directly contradicts the "only"/closed-list statements at 156 and 165, and (b) offers an "array order" fallback that is provably insufficient for this grouping: two over-content beats clamp to the *same* resolved X (e.g. `beat: 50` and `beat: 99` both clamp to `scaledContent − NOTE_CLAMP_INSET`), so a writer who only kept resolved X / array order cannot reconstruct the design's raw-beat groups — and grouping by epsilon-rounded resolved X is the alternative the design **explicitly rejected** (design Decision "Uniform outward stacking", alternative 2). The per-event path does not have this problem (per-event anchor = the event itself, and `collectEventTexts` pushes an event's notes consecutively at one X, so array order suffices — Task 4 line 131 / Task 7 line 233 are self-consistent). The defect is specific to the standalone path, whose anchor is non-positional `(staff, placement, raw beat)`.

**Where in plan:** Task 5 Changes (lines 156–157) and Acceptance (line 165) vs. Task 8 Changes (line 257) and Acceptance (line 272). The design has the same latent gap: its normalized emit primitive `{ kind: "note", x, text, placement, staff? }` (design line 91) omits raw `beat`, yet its stacking decision (design line 200) requires grouping standalone notes "by the **raw** beat (pre-interpolation)".

**Suggestion:** Make Task 5 store the raw beat (or a precomputed group key / within-group stack index) on each `standaloneNotes` record, and make the record-shape statements agree. Concretely: (a) add the raw `beat` group key to the record (e.g. carry `beat` as-is, or store `group: \`${staff}|${placement}|${beat ?? "noBeat"}\``, or precompute and store `k`/`stackIndex` per `(staff, placement, raw beat)`); (b) replace the "carries `x`, `text`, `placement`, `staff` only" wording at line 156 and the closed acceptance list at line 165 to include that field; (c) drop the insufficient "or keep array order within a group" escape hatch at line 157 (or qualify it to "array order *plus* the raw-beat group key"); and (d) make Task 5's acceptance assert the stored grouping field exists and that two same-`(staff, placement, raw beat)` notes share a group while `beat: 2` vs `beat: 2.0001` do not. Then Task 8's "group from Task 5" instruction and its line-272 acceptance become satisfiable from the record alone, with no source re-read.

**Why it matters:** Each task is dispatched verbatim to a fresh, sequential code-writer. A Task 5 writer following its acceptance literally produces records without raw beat; the Task 8 writer then cannot honor "group from Task 5" or its own line-272 acceptance and is forced into either re-reading `measure.notes` (not what Task 8 says) or design-rejected resolved-X grouping (which silently merges two clamped beats and drops a node). That is the "two independent code-writers diverge" failure, and it directly endangers a traced spec AC — Requirement 20 / "N same-placement notes at N distinct positions, none lost, none overlapping" for standalone notes. The fix is a single stored field plus making the two sections agree.
