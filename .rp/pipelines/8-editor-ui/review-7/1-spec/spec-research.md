## Review intent (from the prompt)

Two distinct natures, both in scope:

1. **A functional regression to fix.** The per-row action buttons (Add / Remove / Duplicate for section, measure, note) are invisible in the real editor, and the hand-row "Add note" button is an empty bordered square with no glyph — while 669 unit tests stay green because the jest harness stubs the very components involved (`DropdownMenu`/`MenuGroup`/`MenuItem`/`Icon` in `test/mocks/wordpress-components.js`, and `@wordpress/icons` mapped to string sentinels in `test/mocks/wordpress-icons.js`), and Playwright e2e cannot run here (wp-env port conflict). Must establish ROOT CAUSE as fact, then require a verification strategy that makes "tests green + buttons invisible" impossible.
2. **Interaction/polish changes.** Adopt the Gutenberg block-menu model (Remove / Duplicate / Add after / Add before — positional insertion at section, measure, AND note level; hand rows keep hosting the empty-hand Add-note entry); align chevrons with row-label text per core's List View; separate the tree from the canvas with clearer space and an editor-native boundary; keep using Gutenberg components throughout.

Carry forward review-6's wins and standing constraints (select-only labels, single expansion Set, coordinate keys, `[aria-level]` indent, recolor-only highlight, TreeGrid keyboard parity; only `@wordpress/*`; song format/`render.php`/front-end SVG byte-identical; raw-JSON mode untouched; valid-by-construction).

The "no ellipsis visible at all" symptom therefore is NOT obviously an icon-element problem; it points at the toggle/cell not rendering or being zero-size/hidden. Root cause needs confirming.
- **The hand-row "Add note" `Button` uses `icon="plus"` — a STRING (a Dashicon slug)**, not a `@wordpress/icons` element (`StructureTree.js:365`). A string icon on `Button` renders a Dashicon `<span class="dashicons dashicons-plus">`, which needs the `dashicons` font stylesheet to show a glyph. The prompt's transcribed screenshot — an empty bordered square — is consistent with the dashicons stylesheet not being loaded where the block edit UI mounts (e.g. the editor canvas iframe). This is the most concrete root-cause lead and is fixable by passing a `@wordpress/icons` element (e.g. `plus` or `plusCircle`) instead of the string.
- **`src/style.scss` (editor region) is layout-glue only** — it has rules for `&__workspace` (flex row), `&__tree` (`flex: 0 1 auto; max-width: 24em`, `[aria-level]` indent, `&-label` truncation), `&__canvas`/`&__canvas-svg`, and the recolor `.is-selected` highlight. So chevron alignment and any toggle sizing/visibility are entirely whatever the unstyled stock components produce in this DOM — a plausible contributor to both the misaligned chevron and (if the toggle has no intrinsic size in this context) the invisible ellipsis.
- **`block.json` declares `editorScript` + a shared `style` (front+editor) but NO `editorStyle`** (apiVersion 3, so the edit UI mounts in the editor canvas iframe). The block ships no editor-only stylesheet, and `src/style.scss` has no rule sizing the action cell / toggle. Whether the `@wordpress/components` build CSS (`wp-components` — which gives the icon `Button`/`DropdownMenu` toggle its size and the `Popover` its styles) is present inside the canvas iframe is a candidate root cause for "toggle in DOM but zero-size/invisible." (To be confirmed by the researcher: does WP auto-enqueue `wp-components` styles into the editor canvas, or must a block depend on / enqueue them?)
- **`edit.js` already owns all mutators** with the exact signatures the menu will call: `onRemoveSection(i)`, `onDuplicateSection(i)`, `onAddMeasure(i)`, `onRemoveMeasure(i,j)`, `onDuplicateMeasure(i,j)`, `onAddNote(i,j,hand)`, `onRemoveNote(i,j,hand,k)`, `onDuplicateNote(i,j,hand,k)`. There is NO positional "add after/before at this index" insertion handler yet for sections/measures/notes — today's adds append (`onAddMeasure` appends; `onAddNote` inserts-after-selection-or-appends; duplicate inserts a copy at index+1). The block-menu model's "Add after/Add before" needs new or reshaped insert-at-index handlers. `songModel.js` already exports `insertAt`, `duplicateAt`, `removeAt`, `newSection`, `newMeasure`, `newNote`.

### Q1 — Root cause of the invisible `DropdownMenu` toggle

**Asked:** against the real `@wordpress/components` source, how `DropdownMenu` renders its toggle and the most likely root cause that a valid `icon={moreVertical}` toggle with forwarded `toggleProps` shows no visible toggle; whether `toggleProps` is the right channel for `{ ref, tabIndex, onFocus }`; "not in DOM" vs "in DOM but invisible"; and what a real-component jsdom test could assert.

**Answer (researcher, against `@wordpress/components` trunk + the WP-6.8 `@wordpress/components@29.5.2` tag, and the installed `@wordpress/icons`):**

> **ROOT CAUSE #1 — no ellipsis toggle = `DropdownMenu` returns `null`.** Core's `DropdownMenu` has an early guard at the TOP of the component: `if ( ! controls?.length && ! isFunction( children ) ) { return null; }` — this returns from the WHOLE component, so NO toggle renders. The shipped tree passes **plain-element** children (`<MenuGroup><MenuItem/></MenuGroup>`) — NOT a function — and passes **no `controls` array**. So every per-row `DropdownMenu` renders **nothing** (toggle not even in the DOM). `renderContent` only renders children via `isFunction(children) ? children(props) : null`. The jest mock hid this because it renders `children` directly regardless of type. **Fix options:** pass `children` as a **render function** `({ onClose }) => <MenuGroup>…</MenuGroup>`, OR use the **`controls={[…]}`** array prop.
>
> **ROOT CAUSE #2 — empty square = string Dashicon slug needs a stylesheet.** `Button` forwards `icon` straight to `<Icon icon={…}>`. A real `@wordpress/icons` `plus` is a pre-rendered **SVG element** (`isValidElement` true → `Icon` does `cloneElement`, inline SVG, no stylesheet needed). The shipped `icon="plus"` is a **STRING** → `Icon` treats it as a **Dashicon slug** and renders `<Dashicon icon="plus">` (class `dashicons-plus`), which needs the **dashicons stylesheet** — not reliably present in the editor canvas iframe → button-shaped outline, no glyph. **Fix:** import `plus` from `@wordpress/icons` and pass `icon={plus}` (element).

**Analyst takeaway:** TWO independent, confirmed root causes, each with a concrete fix. The `DropdownMenu` `return null` is the PRIMARY regression (no toggle at all); the string-icon is the secondary (empty-square hand button). This supersedes my local "zero-size/CSS" guess — the toggle is simply not in the DOM. The regression-fix requirement MUST name both fixes; the verification requirement must close the specific gap the jest `DropdownMenu` mock created (it renders element children unconditionally, so it can NEVER reproduce the `return null` guard).

**Confirming detail (researcher's second pass — root cause #1 raised to ~100%, alternatives ruled out):**
- **Version pin.** `@wordpress/icons@10.32.0` and `@wordpress/components@30.5.0` published the same minute (2025-10-01) from the same Gutenberg train; WP 6.9 ships components 30.6.x. The guard is **byte-identical in behavior across components 29.5.2 (WP 6.8), 30.6.4 (WP 6.9), and trunk** — version-robust. Cite: `components/src/dropdown-menu/index.tsx`, `UnconnectedDropdownMenu`, top-of-body guard `if ( ! controls?.length && ! isFunction( children ) ) { return null; }`.
- **Icon is NOT the problem.** When the guard does not fire, the toggle is a `Button icon={moreVertical}` → inline SVG, NO dashicons sheet needed. Dashicons CSS is required only for a STRING icon (the hand-row `icon="plus"` bug).
- **toggleProps/ref forwarding is CORRECT, not the cause.** Real chain `TreeGridCell` → `TreeGridItem ref={ref}` → `RovingTabIndexItem` calls the render-prop with `{ ref, tabIndex, onFocus, ...props }`; forwarding via `toggleProps` is the right channel (merged onto the toggle `Button`, a forwardRef) — exactly how core's List View wires its row action button into roving tabindex. It just never runs because the guard returns null first.
- **Definitively "not in the DOM"** (whole subtree removed) → the fix is API/contract, not CSS.
- **`onClose` bonus:** render-function form gives `({ onClose }) => …`, so each handler can `onClose()` after acting (plain-children form lacks this); effectively the form core's block menu uses.
- **`controls` CAN group:** `controls` accepts `DropdownOption[][]` (array-of-arrays) for multiple visually-separated groups and auto-closes on click — so it could isolate Remove. (Q6a settles render-function vs `controls`; render-function is the minimal-diff path preserving today's `MenuGroup`/`MenuItem`/`isDestructive` markup.)

### Q2 (pre-answered in the researcher's first reply) — Verification strategy within this environment's limits

**Researcher's finding:** The real `@wordpress/components` and `@wordpress/block-editor` are **NOT installable** here — the build externalizes them to `wp.*` runtime globals, so jest MUST mock them; **there is no real components source to render in jsdom.** ONLY `@wordpress/icons` is a real installed dependency. Consequences:

> - A feasible real-component-level guard: render the tree with the **REAL `@wordpress/icons`** (un-map it from the string mock) to assert the chevron/menu/Add icons are actual **inline SVG**, not strings — that alone would have caught the `icon="plus"` regression.
> - **React-singleton gotcha (verified experimentally):** the icons package nests its own **React 18.3.1**, while the project's top-level React is **19.2.7**; real icon elements fail `isValidElement` under the top-level React and throw "Objects are not valid as a React child" UNLESS jest dedups React to a single (18.x) copy via `moduleNameMapper`/resolver.
> - **The `DropdownMenu` `return null` regression specifically CANNOT be caught by real `@wordpress/components`** (not installable). It has to be caught by a **contract-shaped assertion** (e.g. assert the children passed to `DropdownMenu` is a render function, or that `controls` is used) or by the **e2e suite**.

**Analyst takeaway — the verification strategy must be a TWO-PART defense, because no single mechanism catches both root causes here:**
1. **Real-icon assertion** (un-mock `@wordpress/icons`, with React deduped to one copy) to catch string-vs-element icon regressions (would have caught #2). This is the "real-component rendering in jsdom" the prompt asks for, scoped to what's actually feasible (only icons are real).
2. **Contract-shaped assertion on the `DropdownMenu` usage** to catch #1 — because the mock structurally cannot reproduce core's `return null` guard, the test must assert the tree satisfies core's contract (children is a render function OR `controls` is supplied), AND/OR the jest `DropdownMenu` mock must be **hardened to mirror core's `return null` guard** so that a non-function-children usage renders no toggle in the mock too (making "tests green + toggle invisible" impossible at the unit layer). Plus e2e kept consistent-by-construction. **Open design choice for later phases; the requirement is the falsifiable outcome.**

**Verified locally (supports the verification requirement's feasibility):**
- React-singleton split confirmed: top-level `react`/`react-dom` are **19.2.7**; `@wordpress/icons` nests its own **react 18.3.1** (`node_modules/@wordpress/icons/node_modules/react`) and `@types/react 18.3.31`. The project's top-level `@types/react` is 19.2.16. So the researcher's gotcha is real on this branch: un-mocking `@wordpress/icons` in jest WITHOUT React dedup would throw "Objects are not valid as a React child" (icon elements built by the nested React 18 fail `isValidElement` under top-level React 19).
- The base `@wordpress/scripts` jest config has an **empty `moduleNameMapper`** (preset `@wordpress/jest-preset-default`, no resolver, no React dedup); the project's `jest.config.js` is the only place `@wordpress/*` are mapped. So a verification approach that un-mocks `@wordpress/icons` MUST add a React-singleton mapping in `jest.config.js` (e.g. map `^react$`/`^react-dom$` to the top-level copy, or map the icons' nested react to the top-level one) so a single React instance is used. This is a concrete, in-scope test-harness change — no runtime dependency added.

### Q5 (pre-answered) — Chevron-label alignment root cause

### Q6 — Which `DropdownMenu` fix to prefer, and the tree/canvas separation token

**Asked:** (a) Does the `controls={[…]}` array prop support per-item `isDestructive` and the {Duplicate, Add before, Add after | Remove} grouping, or does it force a flat undivided list — vs. render-function children preserving today's `MenuGroup`/`MenuItem`/`isDestructive` grouping with `onClose()` to close after an action? (b) How does core natively separate the List-View rail from the canvas (border-inline-end / shade / gap), and is there a stock CSS custom property / token a third-party block can cite so the divider isn't a hardcoded hex?

**Verified locally (constrains how the tree/canvas separation requirement can be phrased):** `src/style.scss` does NOT `@import`/`@use` `@wordpress/base-styles`; the `@wordpress/scripts` webpack does NOT auto-inject base-styles (no `additionalData`/`includePaths`); and `@wordpress/base-styles` is only a TRANSITIVE dependency, not a direct one. So the SCSS tokens `$gray-*` / `$grid-unit-*` / `$border-width` are NOT resolvable in this block's stylesheet today without adding an `@import`. (NOTE: the researcher's A6b corrects part of this — see below: base-styles IS installed and sass-loader resolves bare `@wordpress/*` specifiers, so an `@use`/`@import` IS feasible without promoting base-styles to a direct dep, though doing so would be cleaner.)

**Answer A6a (researcher — render-function children, ruling out `controls`):**
- **`controls` grouping: supported** — `controls?: DropdownOption[] | DropdownOption[][]`; a nested array renders multiple groups and `renderContent` adds `has-separator` to the first item of each set after the first.
- **`controls` `isDestructive`: NOT supported** — the `DropdownOption` type (`components/src/dropdown-menu/types.ts`) has only `icon?`, `title` (required), `isDisabled?`, `onClick?`, `isActive?`, `label?`, `role?`. No `isDestructive`; each control renders as a plain `<Button size="compact">` (not `<MenuItem>`), so Remove would be a normal (non-red) item — destructive affordance lost.
- **Render-function children PRESERVES everything, minimal diff** — `children={ ({ onClose }) => ( <MenuGroup>…</MenuGroup> ) }` keeps the EXACT `MenuGroup`/`MenuItem`/`isDestructive` markup the rows already build; the only change is wrapping today's JSX in `({ onClose }) => ( … )`. This is the form core's own block settings menu uses (Delete isolated in a trailing `MenuGroup`).
- **`onClose` is idiomatic** — core calls the close in each handler: `onClick={ () => { handler(); onClose(); } }`. Genuine bug-fix bonus: the current plain-element form had NO access to `onClose`, so even had it rendered, the menu wouldn't auto-dismiss after an action.

**Answer A6b (researcher — `$gray-300`/#ddd vertical rule + more gap):**
- **The token: `$gray-300: #ddd`** — base-styles source comments it `// Used for most borders.` (verified in installed `node_modules/@wordpress/base-styles/_colors.scss`; neighbors `$gray-200 #e0e0e0` "light borders", `$gray-100 #f0f0f0` "light gray backgrounds"). This is the editor-native border token to cite.
- **It is a COMPILE-TIME SCSS var, not a runtime CSS custom property.** There is NO portable runtime `--wp-*` var for a neutral panel-border gray usable in the canvas iframe — core only exposes runtime vars for the ACCENT/focus color (`--wp-admin-theme-color`, `--wp-admin-border-width-focus`). So `var(--wp-…)` cannot get you #ddd.
- **Two in-bounds options:** (1) `@use "@wordpress/base-styles/colors";` (or `@import`) at the top of `src/style.scss` and use `colors.$gray-300` — FEASIBLE here: base-styles is installed and `@wordpress/scripts`' sass-loader resolves bare `@wordpress/*` specifiers through webpack (proven by the existing `url("./notation/pb-music.woff2")`); cost is one import line, benefit is the value tracks core. (2) Hardcode `#ddd` with a comment ("core's `$gray-300`, the standard editor border gray") — zero import, value stable for years, matches the file's current import-nothing style.
- **What core actually uses between the List-View rail and the canvas:** the List View component draws NO divider itself (only focus/selection box-shadows); the separation is owned by the containing secondary-sidebar PANEL with its own edge. Core-idiomatic recipe to reproduce "a clear distinction" in this flex row: **(a) `border-inline-end: 1px solid $gray-300` on the tree column** (a vertical rule; logical property → RTL-safe, respecting the existing `isRTL()` handling), and **(b) more breathing room** — bump the current `gap: 1em` and/or add `padding-inline-end` on the tree so the rule isn't crammed against labels. An optional faint `background: $gray-100` shade reads as a panel too, but a single hairline rule + more gap is the minimal, most List-View-like answer.

**Analyst takeaway (closes the queue):**
- **A6a settles RQ-REG-1 / RQ-MENU-1:** spec **render-function children returning the existing `MenuGroup`/`MenuItem` tree, with `onClose()` in each item handler**, as the strong default. Explicitly rule OUT `controls` for THIS menu because it cannot mark Remove destructive (it can group, but loses `isDestructive` and `MenuItem` semantics). This is the minimal-diff fix that simultaneously unblocks the toggle (root cause #1), preserves grouping + destructive marking, and adds auto-dismiss.
- **A6b settles RQ-SEP-1:** spec a **`border-inline-end: 1px solid` in core's `$gray-300` / #ddd on the tree column, plus increased gap / `padding-inline-end`** (logical properties, RTL-safe). Cite the token by NAME; leave import-vs-literal to the design/code phase (both in-bounds: `@use "@wordpress/base-styles/colors"` is feasible since sass-loader resolves `@wordpress/*`, OR a commented `#ddd` literal). NOT a runtime `var(--wp-…)` — none exists for a neutral border gray. This is layout-glue, not a design language.

### Group REG — Fix the functional regression (the invisible row actions)

- **RQ-REG-1 (MUST) — Per-row action menus actually render at section, measure, AND note level.** The per-row `DropdownMenu` MUST be invoked so core's `UnconnectedDropdownMenu` guard (`if ( ! controls?.length && ! isFunction( children ) ) return null;`) does NOT fire — i.e. the menu MUST pass either **children-as-a-render-function** (`({ onClose }) => …`) or a non-empty **`controls` array**. The shipped plain-element children (`<MenuGroup><MenuItem/></MenuGroup>`) are the regression and MUST be replaced. _Strong default:_ **render-function children** (minimal diff; preserves the existing `MenuGroup`/`MenuItem`/`isDestructive` grouping; yields `onClose` to dismiss the menu after an action). `controls={DropdownOption[][]}` is an allowed alternative (it can still separate the destructive group) but rewrites the markup. Each action handler SHOULD call `onClose()` after acting.
- **RQ-REG-2 (MUST) — The hand-row "Add note" button shows a real glyph.** The hand-row `Button` MUST pass a `@wordpress/icons` **element** (e.g. `plus` imported from `@wordpress/icons`), NOT the string slug `icon="plus"`, so it renders inline SVG without depending on the dashicons stylesheet (which is not reliably present in the editor canvas iframe). The empty-bordered-square is the regression and MUST be gone.
- **RQ-REG-3 (MUST) — Verification makes "tests green + actions invisible" impossible.** The unit suite MUST gain a guard that fails when the row-action menu would not render. Because the REAL `@wordpress/components` is not installable here (externalized to `wp.*` globals; only the jest mock exists), this is a TWO-PART defense:
  - **(3a) Contract guard for the toggle (root cause #1).** Either harden the jest `DropdownMenu` mock to MIRROR core's guard — render `null` (no toggle) when `typeof children !== "function" && !controls?.length` — so the existing menu-item assertions go red the instant plain-element children are passed; and/or add an explicit assertion that the tree satisfies core's contract (render-function children, or `controls` supplied). The hardened-mock path is the highest-leverage, zero-dependency option and directly closes the gap that blinded review 6.
  - **(3b) Real-icon guard for the glyph (root cause #2).** Render the tree with the REAL `@wordpress/icons` (un-mapped from the string-sentinel mock) and assert the row-action / chevron / Add-note icons are actual **inline `<svg>`**, not strings/Dashicon classes. This requires deduping React in jest (verified: top-level `react`/`react-dom` 19.2.7 vs the icons package's nested react 18.3.1; `@wordpress/icons` `@types/react` 18.3.31), via a `moduleNameMapper`/resolver entry in `jest.config.js` mapping React to a single copy — a test-only harness change, NO runtime dependency added.
  - **(3c) e2e consistent-by-construction.** The Playwright specs (which cannot run here) MUST be updated to match the new menu (item names, render-function path) so they stay honest for when the environment can run them. They are NOT the primary guard for this environment (they never executed and that is how the regression escaped).

### Group MENU — Adopt the Gutenberg block-menu model

- **RQ-MENU-1 (MUST) — Block-menu item set + grouping at every level.** Each section, measure, and note row's actions menu MUST offer **Duplicate, Add before, Add after** in a primary group and **Remove** isolated in a separate destructive group below it (Remove marked `isDestructive`), mirroring core's block-settings menu (core's labels are exactly **"Add before"/"Add after"**; Remove/Delete sits in its own final group). Out-of-scope core items (Move up/down, Copy/Cut, styles) are NOT included — there is no clipboard/style model for song nodes. This REPLACES the current per-kind item sets ("Add measure" in the section menu, etc.).
- **RQ-MENU-2 (MUST) — Positional insertion handlers, valid-by-construction.** "Add before"/"Add after" MUST insert a fresh schema-conformant node (`newSection()`/`newMeasure()`/`newNote()`) at `index` ("before") or `index + 1` ("after") via `insertAt`, at section, measure, AND note level. `edit.js` has NO such handlers today (only append-style `onAddSection`/`onAddMeasure`/`onAddNote` and `onDuplicate*`); new insert-at-index handlers MUST be added (built on `songModel.js`'s existing `insertAt`/`newX()`), each routing through `commit` (which re-validates). Newly inserted nodes SHOULD be auto-selected and their ancestors revealed, mirroring the existing duplicate handlers, so the new node is visible and selected.
- **RQ-MENU-3 (MUST) — Hand rows keep the direct "Add note" entry.** Hand-group rows are NOT block-menu rows; they retain the single direct "Add note" `Button` (now with an element icon per RQ-REG-2) as the way to seed the FIRST note of an empty hand (where "before/after" has no anchor). The Note-panel contextual "Add note" also stays.

### Group POLISH — Alignment & separation

- **RQ-ALIGN-1 (MUST) — Chevron vertically centered on the row label.** The disclosure chevron MUST sit vertically centered against the row label text, matching core's List View (`ListViewExpander`): a CSS-only fix in `style.scss` — the row's label cell laid out as a flex line with `align-items: center`, and the expander a fixed square box sized to the icon. NO markup change to `TreeExpander` (it already mirrors core's structure). The icon-swap-vs-rotate difference from core is cosmetic and out of scope.
- **RQ-SEP-1 (MUST) — Editor-native separation between the tree and the canvas.** The structure tree and the canvas MUST read as clearly separated with more space and a clear visual boundary, using editor-native styling (no bespoke design language). Concretely: a **`border-inline-end: 1px solid` vertical rule on the tree column in core's standard border gray `$gray-300` (#ddd)**, plus **increased gap and/or `padding-inline-end`** so the rule isn't crammed against the labels. The separation MUST use **logical properties** (`border-inline-end`, not `border-right`) so it respects the existing `isRTL()` direction handling. The exact color MUST be core's `$gray-300`/#ddd; the design/code phase MAY express it either as `@use "@wordpress/base-styles/colors"` → `colors.$gray-300` (feasible: base-styles is installed and `@wordpress/scripts`' sass-loader resolves bare `@wordpress/*` specifiers — proven by the existing `url("./notation/pb-music.woff2")`) OR as a commented `#ddd` literal. A runtime `var(--wp-…)` is NOT available for a neutral border gray (core exposes runtime vars only for the accent/focus color), so the requirement does not depend on one. An optional faint `$gray-100` (#f0f0f0) panel-shade on the tree column is allowed but not required; the hairline rule + more gap is the minimal, most List-View-like answer.
