## Analyst's local harness verification (the React-dedup mechanics, proven on-branch before the Q&A)

_These commands ran against the installed `node_modules` on `worktree-8-editor-ui`. They settle the EXACT `jest.config.js` change the real-icon guard (R-REG3b) needs — a code-phase-saving fact, since a partial mapping silently breaks._

- **The split is a multi-package nested tree, not just `react`.** `@wordpress/icons@10.32.0` ships its OWN nested copies of `react` **18.3.1**, `react-dom` 18.3.1, `scheduler`, `@wordpress/element`, and `@wordpress/primitives` under `node_modules/@wordpress/icons/node_modules/`. Top-level `react`/`react-dom` are **19.2.7**. The icon SVG elements (`chevron-right-small.js` etc.) are pre-built with `import { jsx as _jsx } from "react/jsx-runtime"`, and `Icon` does `cloneElement(icon, …)` importing `cloneElement` from `@wordpress/element`. So the element-creating React for icons is the **nested 18.3.1** via `react/jsx-runtime`, resolved through the icons package's nested `@wordpress/element` → nested `react`.
- **The failure is a `$$typeof` Symbol mismatch.** React 18 tags elements `Symbol.for('react.element')`; React 19 tags them `Symbol.for('react.transitional.element')`. Verified: an element built by the icons' nested-18 `react/jsx-runtime` returns `React19.isValidElement(...) === false`. This is exactly the "Objects are not valid as a React child" throw the spec-research predicted — it is a Symbol-identity problem, not a version-number problem, so it cannot be papered over.
- **A PARTIAL mapping is actively dangerous.** Mapping only `react` → top-level 19 while `react-dom` stays nested-18 throws `Cannot read properties of undefined (reading 'ReactCurrentDispatcher')` — a nested react-dom 18 reading a top-level react 19's internals. So the design MUST map the WHOLE React surface consistently to one copy, or none of it.
- **The full, consistent mapping WORKS — verified end-to-end.** With `react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `react-dom`, `react-dom/client`, and `scheduler` ALL resolved to the top-level copy, the real `@wordpress/icons` exports `chevronRightSmall`, `plus`, and `moreVertical` each pass `React.isValidElement(...) === true` and carry a real SVG element type. All six target modules exist at top level (`require.resolve` succeeds for each). **This is the exact `moduleNameMapper` set the code phase needs.** Mapping just `^react$`/`^react-dom$` is INSUFFICIENT (misses `react/jsx-runtime`, which the automatic JSX runtime — see next bullet — uses).
- **The automatic JSX runtime makes `react/jsx-runtime` non-optional.** `@wordpress/babel-preset-default` (what `@wordpress/scripts` applies to test + source JSX) uses `runtime: 'automatic'` — so the test files AND `StructureTree.js` compile to `react/jsx-runtime` `_jsx(...)` calls, not `React.createElement`. Both the test renderer and the icon elements must therefore share ONE `react/jsx-runtime`, or the host tree and the icon child disagree on the element Symbol.
- **The base jest layers do NOT dedup React.** `@wordpress/scripts/config/jest-unit.config.js` → preset `@wordpress/jest-preset-default` whose `moduleNameMapper` maps only `*.scss/css` and `@eslint/eslintrc` (plus `modulePaths: ['<rootDir>']`, `testEnvironment: 'jsdom'`). The project's own `jest.config.js` is the ONLY place `@wordpress/*` are mapped and is the ONLY place to add the React-dedup mapping. This is a test-only `moduleNameMapper` addition — **NO runtime dependency** (R-KEEP2 holds).
- **A thin element-rendering `Icon` mock is a feasible, honest real-icon guard — verified.** With React deduped, a minimal Icon stand-in `({ icon }) => React.isValidElement(icon) ? React.cloneElement(icon) : null` renders a REAL inline `<svg>` for the element `plus`/`moreVertical`/`chevronRightSmall` (e.g. `<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" …>`), but renders **nothing (empty string)** for the STRING `"plus"` (`isValidElement('plus')` is false). So a test that un-maps `@wordpress/icons` (real elements) AND swaps in this element-rendering `Icon` mock, then asserts a row's chevron / Add-note / toggle area contains an `<svg>`, **passes for `icon={plus}` and FAILS for `icon="plus"`** — catching root cause #2 exactly. This sidesteps the fact that the real `@wordpress/components` `Icon` is not installable: we don't need it, only a stand-in that renders whatever element it's handed (mirroring the real `Icon`'s `cloneElement(icon)` behavior). Feeds Q6.4.

## Analyst's positional-insertion analysis (groundable from the on-branch `edit.js`/`songModel.js`)

_Working hypothesis for the `Add before`/`Add after` model (R-MENU2), distilled from the existing mutators. Confirmed/refined against the researcher in the Q&A below._

- **The existing handlers already establish the immutable-splice + commit + auto-select + reveal pattern** the new ones mirror. `onDuplicateMeasure` is the closest template: it `duplicateAt(section.measures, measureIndex)` (insert at `index+1`), rebuilds `section → sections` with `.map`, `commit(...)`, then `setSelection({ kind: "measure", sectionIndex, measureIndex: measureIndex + 1 })` and `revealAncestors(expansionKey({ sectionIndex }))`. The positional inserts replace `duplicateAt(list, i)` with `insertAt(list, target, newX())` where `target = i` (before) or `i + 1` (after), and select `target` (not `i+1`).
- **Six call sites, one shape.** Section / measure / note × before / after. The `songModel.js` primitives (`insertAt`, `newSection`, `newMeasure`, `newNote`) already exist; only `edit.js` handlers are new. Open: spell out six named handlers (`onAddSectionBefore/After`, `onAddMeasureBefore/After`, `onAddNoteBefore/After`) for symmetry with the existing per-kind handlers the tree already wires, OR parameterize as three `onAddSectionAt(i, where)` etc. — to settle in the Q&A (lean: per-kind before/after pair, because the tree's `DropdownMenu` items are static and the existing handler-prop surface is already per-kind/explicit).
- **Valid-by-construction holds trivially** (R-KEEP5): each `newX()` is schema-conformant and `commit` re-validates. `insertAt` at `index` or `index+1` over a valid list yields a valid list; no index can be out of `[0, len]` because the menu's `index` is the row's own coordinate.
- **The empty-hand boundary is NOT a positional-insert case** (R-MENU3). Note `Add before`/`Add after` only appears on EXISTING note rows (anchored at a real `eventIndex`), so there is always an anchor. Seeding the FIRST note of an empty hand stays the hand-row direct "Add note" `Button` (which appends/insert-after-selection). So the note-level before/after never has to handle an empty `[hand]` list — that path is the hand button's job. (Confirm the hand-key drop/rebuild interplay: a note insert into a non-empty hand keeps the hand key present, so no `delete measure[hand]` dance like `onRemoveNote` — insert only ever grows the list.)
- **Auto-select + reveal mirror the duplicate handlers** (R-MENU2 SHOULD): after inserting, `setSelection` the new node's coordinate (`target`) with its `kind`, and `revealAncestors(...)` the new node's ancestor expansion keys (section for a measure; section+measure+hand for a note) so the new row is visible and selected. A section insert needs no reveal (top level always visible), matching `onDuplicateSection` (which seeds nothing).

**Analyst decision — POSITIONAL INSERTION (settled; the named-vs-parameterized question is resolved by A1's canonical template):**
- **Six named per-kind before/after handlers in `edit.js`:** `onAddSectionBefore(i)` / `onAddSectionAfter(i)`; `onAddMeasureBefore(i, j)` / `onAddMeasureAfter(i, j)`; `onAddNoteBefore(i, j, hand, k)` / `onAddNoteAfter(i, j, hand, k)`. Chosen over a parameterized `onAddXAt(coords, where)` because (a) A1's canonical menu template wires these exact names as static `MenuItem` `onClick`s, (b) it mirrors the existing per-kind explicit handler-prop surface the tree already uses (`onDuplicate*`/`onRemove*`), and (c) the `DropdownMenu` items are static — there's no runtime `where` to thread, so a parameter buys nothing and costs a closure at each call site. (A thin internal shared helper `insertNodeAt(list, target, factory)` MAY back the six to avoid copy-paste, but the PROP surface stays six named handlers.)
- **Each handler:** compute `target = index` (before) or `index + 1` (after); `insertAt(list, target, newX())` at the right depth (rebuilding `section → sections` / `measure → measures` immutably exactly as the duplicate handlers do); `commit(...)` (re-validates, R-KEEP5); `setSelection({ kind, …coords with the inserted index = target })`; `revealAncestors(...)` the new node's ancestor keys (none for a section; `expansionKey({ sectionIndex })` for a measure; section+measure+hand for a note). Valid-by-construction (R-MENU2): `newX()` is schema-conformant, `insertAt` over a valid list at `[0,len]` stays valid, index always in range (it's the row's own coordinate).
- **Note before/after never touches an empty hand** (R-MENU3): the items appear only on existing note rows (real `eventIndex`), so the `[hand]` list is non-empty and insertion only grows it — NO `delete measure[hand]` rebuild like `onRemoveNote`. Seeding the first note of an empty hand stays the hand-row "Add note" `Button`; the Note-panel "Add note" also stays. All three note-add affordances coexist (verified: `NotePanel` keeps its own `onAddNote`/`onRemoveNote`).
- **The orphaned `onAddMeasure(sectionIndex)` (append) is NOT deleted** — per the Q2 decision it moves to a `SectionPanel` "Add measure" button (the zero-measure-section appender). So `edit.js` ends with: the six new positional handlers + the retained append `onAddMeasure` (now Section-panel-driven) + the unchanged hand-row `onAddNote` + `onDuplicate*`/`onRemove*`. `onAddSection` (append) likewise stays for the Song panel's "Add section".

## Open issue the analyst surfaced (the zero-measure-section recovery gap) — RESOLVED in Q2

_Found while grounding the menu reshape against the on-branch code. Put to the researcher in Q2 and SETTLED there: adopt option (iii), a `SectionPanel` "Add measure" button reusing the orphaned `onAddMeasure` (core's `BlockListAppender` idiom). Kept here as the discovery trail; see the Q2 entry for the decision + grounding._

- **Removing "Add measure" from the section menu (R-MENU1) eliminates the ONLY way the editor can add a measure to a section that has ZERO measures.** Verified on-branch: (a) the schema (`src/song/schema.js`) requires `measures` but sets NO `minItems`, so `measures: []` is conformant; (b) `onRemoveMeasure` has no last-measure guard, so removing a section's last measure is allowed and leaves `measures: []`; (c) the section menu's `onAddMeasure` is the SOLE "Add measure" entry point in the whole editor — `SectionPanel` has no add-measure control, and the new block menu puts "Add before/after" only on MEASURE rows (a zero-measure section has none). So after the reshape, a section emptied of measures becomes a dead end in the visual editor (only raw-JSON can re-seed it).
- **Why it is likely NOT blocking, but must be DECIDED:** a fresh `newSection()` always seeds one measure, and the common path keeps ≥1 measure, so the gap is an edge case — but it is newly *unrecoverable* in the tree, which review 6's section menu could recover. Candidate resolutions to weigh in Q2: (i) accept it (edge case, raw-JSON escape hatch exists) and note it; (ii) guard `onRemoveMeasure` to refuse removing a section's last measure (mirrors how core won't leave certain containers empty); (iii) keep a single non-block-menu "Add measure" affordance somewhere (e.g. the Section panel) outside the row menu, which R-MENU1 does not forbid (it only reshapes the row MENU). Resolution must trace to a requirement or escalate as a spec gap.

### Q1 — The render-function `DropdownMenu` composition, byte-precise (the regression fix + the menu reshape together)

**Asked:** against the real `@wordpress/components` `dropdown-menu/index.tsx` (`UnconnectedDropdownMenu`/`renderContent`): the exact render-prop signature; whether core's block-settings menu returns multiple sibling `MenuGroup`s in a fragment; `onClose` focus/close semantics + handler order; whether `isDestructive` is a real `MenuItem` prop and the accessible name comes from text children; whether `toggleProps` still merges under the render-function form; and the exact canonical section-row JSX.

**Answer (researcher, against `@wordpress/components` trunk; guard/shape byte-identical across 29.5.2 / 30.6.x / trunk):**

1. **Signature + grouping.** `Dropdown` builds ONE `args = { isOpen, onToggle, onClose }` (`dropdown/index.tsx`) passed to both `renderToggle` and `renderContent`; `DropdownMenu.renderContent` does `isFunction(children) ? children(props) : null`, so a function child is invoked with `{ isOpen, onToggle, onClose }` — destructuring just `{ onClose }` is exactly core's idiom. Multiple sibling `MenuGroup`s in one fragment IS the canonical pattern: core's `block-settings-dropdown.js` returns `({ onClose }) => (<> …primary MenuGroup… { canRemove && <MenuGroup><MenuItem>Delete</MenuItem></MenuGroup> } </>)` — destructive item isolated in its own TRAILING `MenuGroup`.
2. **`onClose` semantics.** `onClose` is the `Dropdown`/`Popover` `close`; calling it closes the popover, and `Popover`'s focus-return restores focus to the trigger on close — this is the mechanism that satisfies R-KEEP4 (not the handler). **Order is NOT load-bearing here:** core actually composes `onClick={ pipe(onClose, handler, …) }` (pipe runs left-to-right, so core closes FIRST), but because our handlers are lifted `edit.js` mutators that `setState`/`commit` (independent React updates, neither reads the other), `() => { handler(); onClose(); }` and the close-first form are equivalent in effect. The spec's `handler(); onClose();` is fine and reads naturally; the only rule is "don't make a handler depend on the menu staying open."
3. **`MenuItem` props.** `isDestructive` is REAL: `MenuItem` doesn't destructure it but spreads `...buttonProps` onto its `<Button>`, and `Button` applies `is-destructive` via clsx → the red treatment. (This is precisely why `controls` can't do it: `controls` render plain `Button`s without the `MenuItem` wrapper.) Accessible name = text children (`<span className="components-menu-item__item">{children}</span>`), so `<MenuItem>{__("Duplicate")}</MenuItem>` etc. give names "Duplicate"/"Add before"/"Add after"/"Remove" and `getByRole("menuitem",{name})` matches. NO `label` prop, NO explicit `role` needed (`MenuItem` defaults `role="menuitem"`). e2e should keep `{ exact: true }` (as the Note-panel "Add note" test already does) so "Add before"/"Add after" don't loosely match other "Add" controls.
4. **Toggle wiring preserved.** The render-function vs plain-element choice affects ONLY `renderContent`; the toggle is built by `renderToggle`, which spreads `mergedToggleProps` (className via clsx, `onClick`/`onKeyDown` chained) onto `<Toggle {...mergedToggleProps} icon={icon}>`. So `toggleProps={{ ref, tabIndex, onFocus }}` still merges onto the toggle `Button` exactly as today — roving-tabindex (R-KEEP4) fully preserved, NO interaction with the children form. The ONLY effect of the render-function change is satisfying the top-of-body guard so the toggle is placed in the DOM at all. Keep `icon={moreVertical}` + `toggleProps` byte-for-byte; only `children` changes.
5. **Canonical section-row template** (only the cell's children change to a render function; the `TreeGridCell` wrapper + `DropdownMenu` `icon`/`toggleProps`/`label` are untouched). Primary group order Duplicate → Add before → Add after; Remove alone in a trailing `MenuGroup` with `isDestructive`. Handler names `onDuplicateSection` / `onAddSectionBefore` / `onAddSectionAfter` / `onRemoveSection`, each wrapped `() => { handler?.(coords); onClose(); }`. Measure/note rows mirror byte-for-byte, differing only in the `label` sprintf and the coordinate args (note rows pass the 4-tuple).
   - **Removal note:** the section menu's old "Add measure" item (today's StructureTree.js:206-208) is REMOVED by R-MENU1 — not part of the {Duplicate, Add before, Add after | Remove} set. "Add measure" capability survives via measure rows' own Add before/after + the `newSection()` seed (which already ships one measure). The reshape must not accidentally keep it.

**Analyst decision (settles the composition):**
- **Adopt render-function children** `({ onClose }) => (<><MenuGroup>{Duplicate, Add before, Add after}</MenuGroup><MenuGroup><MenuItem isDestructive>{Remove}</MenuItem></MenuGroup></>)` at section, measure, AND note level, byte-mirroring core's block-settings menu. Minimal diff that (a) satisfies the `return null` guard → toggle renders (R-REG1), (b) preserves `MenuGroup`/`MenuItem`/`isDestructive` markup + the `toggleProps` roving-tabindex wiring (R-KEEP3/R-KEEP4), (c) yields `onClose` for auto-dismiss, (d) reshapes to the block-menu item set (R-MENU1).
- **Each item handler is `() => { handler?.(coords); onClose(); }`** — act then dismiss; order not load-bearing per the evidence. Keep the `?.` optional-chaining the current code uses.
- **Item set identical in shape at all three levels;** only `label` sprintf + coordinate args differ (section `sectionIndex`; measure `(sectionIndex, measureIndex)`; note the full 4-tuple).
- **`controls` ruled OUT** (re-confirmed): plain `Button`s lose the `MenuItem`+`isDestructive` red treatment R-MENU1 requires.
- **No `label`/`role` on `MenuItem`s; no markup change to the toggle** — `icon={moreVertical}` + `toggleProps={{ ref, tabIndex, onFocus }}` stay byte-for-byte.
- **New handler props `onAddSectionBefore/After`, `onAddMeasureBefore/After`, `onAddNoteBefore/After`** wired into the tree alongside `onDuplicate*`/`onRemove*`; the old `onAddMeasure` tree prop is dropped (the section menu no longer calls it). `onAddMeasure` (append) + the hand-row `onAddNote` stay in `edit.js`; `onAddMeasure` may lose its only tree caller — feeds the zero-measure-recovery decision (Q2).

### Q2 — The zero-measure-section recovery gap

**Asked:** how core handles a container block emptied of all children (guard vs appender vs accept), and which of (i) accept + document, (ii) guard `onRemoveMeasure` against removing the last measure, (iii) keep one non-row "Add measure" affordance is most core-idiomatic.

**Answer (researcher, against `block-editor/src/components/block-list-appender/index.js`):** Core's container blocks NEVER dead-end. `BlockListAppender` renders a default appender whenever `getBlockCount(rootClientId) === 0` (its own comment: "The appender exists to let you add the first Paragraph before any is inserted") — `DefaultBlockAppender` falling back to `ButtonBlockAppender`. Core's invariant is **an emptied container still shows a persistent "+" appender**, and core does NOT block removing the last child. So:
- **(ii) Guarding removal is ANTI-core** — core never blocks the delete; it provides a re-add path instead. A last-measure special-case would be a surprising exception in an otherwise uniform remove. Recommend against.
- **(iii) One non-row "Add measure" affordance is the most core-idiomatic** — the direct analog of core's persistent appender. Natural home: **`SectionPanel`** (it already receives `working`/`selection`/`onChange`/`onRemoveSection`; add an "Add measure" button calling the EXISTING append-style `onAddMeasure(sectionIndex)` from `edit.js:261`, which R-MENU1 otherwise orphans). Keeps the capability for the always-available case without re-introducing it as a tree-row menu item (which R-MENU1 forbids).
- **(i) Accept + document is weakest** — a real dead-end in the visual editor for a schema-legal state, exactly the "unreachable affordance" class this whole review exists to kill.

**Analyst decision (settles the zero-measure recovery; small scope addition flagged):**
- **Adopt (iii): an "Add measure" `Button` in `SectionPanel`, reusing the already-present `onAddMeasure(sectionIndex)` handler.** This mirrors core's "container always has an appender" invariant, keeps the menu reshape clean (R-MENU1's row-menu set stays exactly {Duplicate, Add before, Add after | Remove}), and closes the dead-end the reshape would otherwise open. NO new mutator — `onAddMeasure` simply stops being orphaned. The Section panel is always reachable when a section/measure/event is selected (R-KEEP6), and a zero-measure section is still selectable as a section row, so the recovery path is always present.
- **Reject (ii)** as anti-core (core never blocks the last-child delete) and reject (i) as re-creating the unreachable-affordance bug class.
- **Scope note (NOT a blocker):** R-MENU1's literal text only says "remove Add measure from the row menu"; it does not mandate a replacement, nor forbid one (it reshapes the row MENU only). Keeping the append-`onAddMeasure` capability alive in `SectionPanel` is the necessary consequence of not silently dropping a capability review 6 shipped — it is squarely inside R-KEEP6 ("every inspector field/affordance reachable today stays reachable"): "Add measure" is reachable today (via the section menu), so a no-regression reading REQUIRES a surviving entry point. I am therefore making this design call within the spec (R-KEEP6 + R-MENU1), not escalating — but the design-writer MUST call it out explicitly so the owner sees the section-menu "Add measure" became a Section-panel "Add measure". If the owner prefers strict minimal-diff, (i)-with-a-doc-note is the documented fallback (defensible because `newSection()` always seeds one measure, so zero-measures only arises by an explicit last-measure removal), but (iii) is the recommendation.
- **Why this is in-spec, not new scope (researcher's deep-dive reinforcement):** (1) The SectionPanel "Add measure" is the section-level mirror of an ALREADY-blessed pattern — R-MENU3 keeps the hand-row direct "Add note" `Button` for exactly the analogous "seed the first child where before/after has no anchor" case. A zero-measure section is the same boundary one level up, so the same non-block-menu-appender answer applies by precedent. (2) The spec's Out-of-Scope bars *new* authoring capability beyond positional add; this is the OPPOSITE — retaining existing capability the reshape would otherwise drop.
