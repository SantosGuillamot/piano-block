## What I verified (the load-bearing claims)

### Root-cause soundness

- **Root cause #1 — `DropdownMenu` renders nothing.** `@wordpress/components` is NOT installed here (externalized to `wp.*`, exactly as the spec states), so the `if ( ! controls?.length && ! isFunction( children ) ) return null;` guard cannot be spot-checked against installed source — it rests on the spec-research evidence that the spec itself already established, which is in-bounds for this phase. The design's **fix** is checkable and correct: `StructureTree.js` today passes plain-element `<MenuGroup><MenuItem/></MenuGroup>` children with no `controls` at all three per-row menus (section `:202-215`, measure `:287-303`, note `:434-460`) and the toggle's `icon={moreVertical}` + `toggleProps={{ ref, tabIndex, onFocus }}` are already correct — so the design's "only `children` change to a render function, toggle byte-unchanged" is precisely the minimal diff. Confirmed `StructureTree.js` is the **only** `DropdownMenu`/`MenuGroup`/`MenuItem` consumer in `src` (the other two greps are the test files), so the hardened mock is safe.
- **Root cause #2 — string Dashicon slug.** Confirmed `StructureTree.js:365` is the literal `icon="plus"` string on the hand-row `Button`; the design's `icon={plus}` (element) fix and "this is THE root-cause-#2 canary; the chevrons/`moreVertical` are already real elements" framing is correct — the chevron path (`<Icon icon={chevronDownSmall|…}>`) and the toggle already pass valid SVG elements, so only the hand-row `plus` was the shipped string.

### The verification design (the part most likely to be wrong — reproduced live)

- **The React split is exactly as described.** `@wordpress/icons@10.32.0` ships nested `react`/`react-dom` **18.3.1** under its own `node_modules`; top-level `react`/`react-dom` are **19.2.7**; the icon SVGs are pre-built with `import { jsx as _jsx } from "react/jsx-runtime"` (verified in `chevron-right-small.js` and `plus.js`). All six React entrypoints (`react`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `react-dom`, `react-dom/client`, `scheduler`) `require.resolve` at top level.
- **The `$$typeof` Symbol mismatch is real.** `React19.isValidElement(realPlus)` is **`false`** (the real `plus` is tagged `Symbol(react.element)` by nested React 18; React 19 expects `Symbol(react.transitional.element)`); the nested-18 `isValidElement(realPlus)` is `true`. So the design's "hard prerequisite" framing is not rhetorical.
- **R-REG3b mechanic, run end-to-end (then deleted).** A throwaway jest test with the six-module dedup mapper added and `@wordpress/icons` left real: `isValidElement(plus|moreVertical|chevronRightSmall) === true`; the element-rendering `Icon` stand-in (`isValidElement(icon) ? cloneElement(icon) : null`) rendered a real inline `<svg>` for `icon={plus}` and **nothing** (no `<svg>`) for the string `"plus"` — using the suite's own `createRoot` + `act` render path (the suite uses `react-dom/client` directly, NOT `@testing-library/react`, which is not installed; the design's pseudo-code is render-path-agnostic and the code phase will use the existing harness's `render`). Re-running the SAME test **without** the dedup mapper failed (2 of 3) — confirming the dedup is a genuine prerequisite, not a nicety. The string→no-svg / element→svg distinction that makes this the regression guard is faithful to production's `cloneElement` path.
- **The un-mapping gotcha is real and correctly flagged.** Under the project's real `jest.config.js`, `jest.requireActual("@wordpress/icons")` resolves **back through the mapper** to the string-sentinel mock (`actual.plus === undefined`; only the four sentinel keys present). The dedicated-config recipe (drop `^@wordpress/icons$` from the mapper + add the dedup) DID resolve `plus` to a real element (`typeof === "object"`, `isValidElement === true`). So the design's "needs `@wordpress/icons` GENUINELY un-mapped (not merely `requireActual` against the still-mapped specifier) AND the six-entrypoint dedup mapper — BOTH" is exactly right, and the §5.2 warning is well-founded.
- **R-REG3a mechanic, run end-to-end (then deleted).** The proposed hardened `DropdownMenu` mock body: plain-element children → renders `null` (no toggle button in the DOM → the existing item assertions go red); a function child → toggle + items render AND `toggle.closest("div")` still resolves (so the existing `buttonByLabel(...).closest("div")` → `selectButtonByText(menuDiv, "Remove")` traversal at `StructureTree.test.js:397-443` survives verbatim) AND the production `() => { handler(); onClose(); }` does not throw with the no-op `onClose`; a non-empty `controls` array → renders (alt path). All three behaviors confirmed. The design's claim that "green tests + invisible toggle" becomes impossible at the unit layer is sound: the regression renders `null`, and every item assertion + the new toggle-presence assertion go red.

### The menu model & positional insertion

- **Menu set/grouping correct.** `{Duplicate, Add before, Add after}` in a primary `MenuGroup` + isolated `{Remove}` in a trailing `MenuGroup` with `isDestructive`, identical in shape at section/measure/note, only the `label` sprintf + coordinate args differing — matches core's block-settings-menu pattern the research cites. The exact labels "Add before"/"Add after" and the `controls`-ruled-out reasoning (plain `Button`s can't carry `isDestructive`) are consistent with the research and the `MenuItem`/`Button` contract.
- **"Add measure" re-home is called out EXPLICITLY and owner-visibly** (§3.3 callout + §8). Verified the gap is real on-branch: schema allows `measures: []` (no `minItems`), `onRemoveMeasure` (`edit.js:279`) has no last-measure guard, and the section menu's `onAddMeasure` is the sole add-measure entry point. The re-home target is grounded: `SectionPanel` already destructures `sectionIndex` from `selection` (`SectionPanel.js:70`) and the "Remove section" `Button` at `:135-141` is a real placement model; `edit.js` renders `<SectionPanel>` (`:511-518`) WITHOUT an `onAddMeasure` prop today, so the design's "add the prop + wire it in `edit.js`" is accurate. `onAddMeasure` (`edit.js:261`) already appends `newMeasure()` and its `sectionIndex = working.sections.length - 1` default is correctly noted. The R-KEEP6 ("Add measure reachable today → must stay reachable") justification is correct, and the anti-core (ii)-guard / weak (i)-accept rejections are well-reasoned against core's `BlockListAppender`.
- **Six positional handlers' shape, valid-by-construction.** `onDuplicateMeasure` (`edit.js:354-371`) is genuinely the closest template (immutable splice + `commit` + `setSelection` + `revealAncestors`); the design's "replace `duplicateAt(list, i)` with `insertAt(list, target, newX())`, select `target` not `i+1`" is the correct delta. `insertAt`/`newSection`/`newMeasure`/`newNote` all exist in `songModel.js` (verified) so no `songModel.js` change is needed — correct. The empty-hand reasoning (note before/after only on existing rows → list always non-empty → no `delete measure[hand]` dance) holds. The auto-select coordinates are sound, and `resolveSelection` (`selection.js:144-154`) **defaults the kind for a complete tuple**, so the design's explicit `setSelection({ kind, … })` is correct and slightly more robust than the existing untagged `onAddNote`. `expansionKey({ sectionIndex, measureIndex, hand })` matches the reveal-ancestors calls.
